Branching model¶

release/X.Y is created at the feature freeze: the first beta, or the first release candidate when there are no betas. Alphas never create a branch. Each step below is the same history, later.

1. v1.1.0 is out. release/1.1 was cut at v1.1.0rc1; merging its release PR tagged v1.1.0, and the changelog was copied back to main. Features keep landing on main. The bot tags the changelog commit v1.2.0.dev0, and writes that version into main's version files if the repository has any: v1.1.0 is never in main's history, so without it versions derived from main (setuptools-scm, hatch-vcs, copier) would sort below v1.1.0. The tag is a development marker, not a release: nothing publishes it.

gitGraph TB:
  commit id: "feat: A" tag: "v1.1.0rc1"
  branch release/1.1
  commit id: "release v1.1.0" tag: "v1.1.0"
  checkout main
  commit id: "changelog v1.1.0" tag: "v1.2.0.dev0"
  commit id: "feat: B"

2. Alphas. Release, minor, alpha tags main's HEAD; each rerun tags the next alpha. No branch, no release PR. Features keep landing.

gitGraph TB:
  commit id: "feat: A" tag: "v1.1.0rc1"
  branch release/1.1
  commit id: "release v1.1.0" tag: "v1.1.0"
  checkout main
  commit id: "changelog v1.1.0" tag: "v1.2.0.dev0"
  commit id: "feat: B" tag: "v1.2.0a1"
  commit id: "feat: C" tag: "v1.2.0a2"

3. Beta: the feature freeze. Release, minor, beta cuts release/1.2 at main's HEAD and tags v1.2.0b1; the release PR opens as a draft. feat: E lands on main after the freeze, so it waits for 1.3. fix: F gets the backport label: because 1.2 is in pre-release, it goes to both lines, tagging v1.2.0b2 and updating the v1.1.1 release PR, which a maintainer merges.

gitGraph TB:
  commit id: "feat: A" tag: "v1.1.0rc1"
  branch release/1.1
  commit id: "release v1.1.0" tag: "v1.1.0"
  checkout main
  commit id: "changelog v1.1.0" tag: "v1.2.0.dev0"
  commit id: "feat: B" tag: "v1.2.0a1"
  commit id: "feat: C" tag: "v1.2.0a2"
  commit id: "feat: D" tag: "v1.2.0b1"
  branch release/1.2
  checkout main
  commit id: "feat: E"
  commit id: "fix: F"
  checkout release/1.2
  cherry-pick id: "fix: F" tag: "v1.2.0b2"
  checkout release/1.1
  cherry-pick id: "fix: F" tag: ""
  commit id: "release v1.1.1" tag: "v1.1.1"
  checkout main
  commit id: "changelog v1.1.1"

4. Release candidates. Release, minor, rc promotes 1.2: it tags v1.2.0rc1 on the branch HEAD (the same commit as v1.2.0b2) and marks the release PR ready. The next backport, fix: G, tags v1.2.0rc2 and still reaches 1.1 (pending v1.1.2).

  commit id: "feat: A" tag: "v1.1.0rc1"
  branch release/1.1
  commit id: "release v1.1.0" tag: "v1.1.0"
  checkout main
  commit id: "changelog v1.1.0" tag: "v1.2.0.dev0"
  commit id: "feat: B" tag: "v1.2.0a1"
  commit id: "feat: C" tag: "v1.2.0a2"
  commit id: "feat: D" tag: "v1.2.0b1"
  branch release/1.2
  checkout main
  commit id: "feat: E"
  commit id: "fix: F"
  checkout release/1.2
  cherry-pick id: "fix: F" tag: "v1.2.0b2 + v1.2.0rc1"
  checkout release/1.1
  cherry-pick id: "fix: F" tag: ""
  commit id: "release v1.1.1" tag: "v1.1.1"
  checkout main
  commit id: "changelog v1.1.1"
  commit id: "fix: G"
  checkout release/1.2
  cherry-pick id: "fix: G" tag: "v1.2.0rc2"
  checkout release/1.1
  cherry-pick id: "fix: G" tag: ""

5. Final and patches. The pending v1.1.2 is merged, then the 1.2 release PR, which tags v1.2.0. From now on 1.1 is unsupported and backports go to release/1.2 only: fix: H updates the v1.2.1 release PR, and merging it ships the patch, with no pre-releases.

Versions of main¶

A development build of main is, for example, a nightly build, pip install git+…@main, or an editable install. This build finds its version in one of two locations:

  • the nearest v* tag in the history of main (setuptools-scm, hatch-vcs, git describe, copier);
  • the version files, with version-files.

These two locations do not contain the versions of the release line. The final tags are only on release/X.Y. The betas and the release candidates after the freeze are also only on release/X.Y. With version files, each pre-release tag points to a commit that is not on main. This commit records the version, and the bot does not push it to a branch.

Thus, after each X.Y.0, the bot changes main to the next series. It tags the commit that the changelog PR adds to main with vX.(Y+1).0.dev0. It also writes this version into the version files.

A .dev version is a pre-release, and nothing publishes it. It is lower than each alpha, beta and release candidate of its version. It is higher than each release before it: 1.1.2 < 1.2.0.dev0 < 1.2.0a1. The tag identifies the next minor release, because the bot cannot know if the next release is a major release. The order stays correct: 1.2.0.dev0 is also lower than 2.0.0a1.

The table shows the version of main at each step of the history above. For versions from tags, the table uses setuptools-scm, one or two commits after the newest tag in the history of main.

Step Newest release of the line main, version from tags main, version files
1. v1.1.0 is out 1.1.0 1.2.0.dev1: higher 1.2.0.dev0: higher
2. Alphas 1.2.0a2 1.2.0a3.dev1: higher 1.2.0.dev0: lower
3. Beta, the freeze 1.2.0b2 1.2.0b2.dev1: lower 1.2.0.dev0: lower
4. Release candidates 1.2.0rc2 1.2.0b2.dev2: lower 1.2.0.dev0: lower
5. v1.2.0 and its patches 1.2.1 1.3.0.dev1: higher 1.3.0.dev0: higher

Known problems¶

In four cases, the version of main is not correct. The examples use the history above.

Problem Steps Builds with the problem main shows The release line has
1. The freeze 3, 4 Version from tags 1.2.0b2.devN 1.2.0b2, 1.2.0rc2
2. Version files 2, 3, 4 Version files 1.2.0.dev0 1.2.0a2 to 1.2.0rc2
3. A late changelog PR 5 Version from tags 1.2.0b2.devN 1.2.0
4. A major release 5 All 1.3.0.devN Next release: 2.0.0

1. The freeze¶

From the cut of release/1.2 to 1.2.0, main shows 1.2.0b2.devN. This version has two errors:

  • it is lower than the betas and release candidates of release/1.2;
  • it identifies the 1.2 series, but the changes on main after the cut go into 1.3.

Cause: the newest tag in the history of main is v1.2.0b1. This tag is on the commit where release/1.2 starts. setuptools-scm calculates the version from this tag.

Why the bot does not tag main at the cut: the commit at the cut is also in the history of release/1.2. A v1.3.0.dev0 tag on this commit also changes the versions of release/1.2 to 1.3.0.devN.

2. Version files¶

This problem applies only to a build that reads its version from the version files. This is usually a build without git metadata, for example a Nix derivation (refer to Adopting release-tools).

  • On main, the files contain 1.2.0.dev0 from 1.1.0 to 1.2.0. This version is lower than each alpha, beta and release candidate of 1.2.
  • On release/1.2, the files contain 1.2.0.dev0 until 1.2.0. After 1.2.0, they contain 1.2.0, also when backports for 1.2.1 have merged.

Cause: only a commit can change the files. The bot writes the files only in the release PR of a final release and in the changelog PR. For a pre-release, the bot writes the version in a commit that only the tag points to. No branch contains this commit.

3. A late changelog PR¶

After 1.2.0, the bot puts the tag v1.3.0.dev0 on the commit that the changelog PR adds to main. If the PR does not merge immediately, the job shows a warning. Until the PR merges, main shows 1.2.0b2.devN. This version is lower than 1.2.0.

Correction: merge the PR. Then start the "Release" workflow run again, to add the tag. If you do not do this, the problem stops at the first alpha of 1.3.

4. A major release¶

The bot cannot know if the next release is a major release. Thus, after 1.2.0, main shows 1.3.0.devN, also when the next release is 2.0.0. The order is correct: 1.3.0.dev1 is lower than 2.0.0a1. But the number is not correct. The number becomes correct at the first alpha, 2.0.0a1.

These problems apply only to the versions of main, and nothing publishes these versions. The problems are important when a build of main must agree with a release. For example, a test environment can require >= the latest release candidate. We accept these problems. Refer to Open questions for the reasons and the solutions that we examined.
